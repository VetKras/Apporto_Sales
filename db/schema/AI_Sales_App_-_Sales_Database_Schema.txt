AI Sales App - Sales Database Schema
Bolt-ready Supabase schema spec

Purpose
This file defines the database schema Apporto Sales should use in Supabase.

Design rules
- Supabase is the normalized source of truth.
- No table should depend on local filesystem paths as truth.
- Pricing models must reference a pricing_config_version.
- Quote lines must store the config version used at calculation time.
- Use JSONB for source traces, metadata, validation results, and flexible deal context.
- RLS can be simple in V1, but fields must support future role/access control.
- Every mutation that changes product, pricing, or competitive truth must be auditable.

Recommended extensions
- pgcrypto for gen_random_uuid()
- vector for knowledge_chunks.embedding

==================================================
RLS V1 GUIDANCE
==================================================

Simple V1 policy is acceptable:
- authenticated users can read core product/pricing/competitive data
- authenticated users can create deals, messages, uploads, feedback, and proposed updates
- only trusted/admin service actions can apply proposed updates

Do not design RLS in a way that prevents future manager/admin/executive workflow expansion.

==================================================
SCHEMA INVARIANTS
==================================================

- Portia is not a product row.
- Pricing values are not permanent constants.
- Exactly one pricing_config_versions row should be active at a time.
- quote_lines must preserve config_version_id for reproducibility.
- source_trace must be preserved for generated outputs.
- conflicts must create ai_events and/or proposed_updates.
- executive overrides require confirmation and audit.
- low-authority conflicts must not alter source truth.
